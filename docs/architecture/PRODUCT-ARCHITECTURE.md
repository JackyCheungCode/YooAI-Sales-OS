# Yooai Sales OS 产品与模块架构

## 产品定位

Yooai Sales OS 是以客户数据为中心、以 AI 智能体为执行能力的全球销售操作系统。业务目标是贯通“发现企业 → 研究与验证 → 潜在客户 → 客户关系 → 销售跟进 → 报价 → 订单”。

本文件定义产品模块边界和实现约束；不表示尚未开发的模块已经上线。

## 一级导航

1. 销售工作台：全球客户看板、客户覆盖、销售漏斗、待办与 AI 洞察。
2. 智能获客中心：地图、搜索、企业网站、授权社交数据源、名单导入与获客任务。
3. 潜在客户管理：线索池、去重、来源证据、AI 画像、评分、联系人验证与转客户。
4. 客户与联系人：企业主档、联系人关系、客户 360、沟通与交易历史。
5. 销售跟进与沟通：活动、任务、邮件、WhatsApp、会议和提醒。
6. 报价管理：产品、价格规则、报价版本、审批、PDF 与报价转订单。
7. 订单管理：订单明细、订单状态、交付、付款信息与异常。
8. AI 智能体中心：自然语言任务、任务规划、执行步骤、工具调用、审批和审计。
9. API 与集成：AI 模型、地图、搜索、企业数据、邮件、WhatsApp 和其他连接器。
10. 系统设置与数据管理：权限、字典、工作流、导入导出、数据质量和审计。

未完成模块必须显示明确的建设状态，不能用模拟业务数据冒充真实记录。

## 分层架构

### 展示层

- Vite + React + TypeScript。
- React Router 提供正式 URL 路由。
- 页面按业务域拆分在 src/modules 下；布局位于 src/layouts。
- 业务控件必须使用 @carbon/react 和 Carbon 官方图标。
- 主题采用 Carbon g10（Gray 10）；正文采用 Productive，字体为 IBM Plex Sans，并按项目规范追加 SimSun。
- 颜色、排版和普通间距使用 Carbon 官方 design tokens；遵守 2x Grid 与响应式规则。

### 业务服务层

- 每个业务域维护自己的类型、服务和页面组件。
- UI 不直接访问第三方数据源；通过受控业务服务或服务端 API 调用。
- 企业发现、来源解析、去重、评分和线索入库分成独立步骤。
- 报价金额、权限校验、订单状态转换等确定性规则不得交给 LLM 自由决定。

### AI 智能体层

- 任务规划器：将自然语言目标转换成结构化任务与步骤。
- 专业能力：获客、企业研究、联系人核验、销售开发、报价辅助、销售运营。
- 工具注册表：每个工具声明输入输出 schema、所需权限、风险级别、超时和重试策略。
- 任务执行器：维护任务状态、步骤状态、取消、重试、审批和结果校验。
- 审计：记录模型、提示版本、工具调用、数据来源、耗时、错误与成本。
- 没有真实模型或连接器时，必须明确标记未配置，不允许静默切换到演示模式。

### 数据与集成层

- Supabase PostgreSQL：业务主数据与任务记录。
- Supabase Auth + RLS：身份认证和行级数据权限。
- 外部 API 凭据和高权限密钥只保存在服务端环境或受控密钥管理中。
- 前端只使用 VITE_SUPABASE_URL 与 VITE_SUPABASE_PUBLISHABLE_KEY；严禁暴露 service-role 或 secret key。
- Vercel 提供部署运行环境；GitHub main 是代码基准。未经明确要求，不手动触发 Preview 或 Production 部署。

## 核心数据关系

- companies：统一企业身份；通过标准化域名、注册信息、地址等辅助去重。
- leads：企业进入销售开发流程后的线索状态、负责人、评分和跟进阶段。
- contacts：联系人身份和企业关系；contact_methods / verification records 维护每种联系方式的来源、验证状态与时间。
- source_evidence：来源 URL、渠道、采集时间、证据摘要和许可/访问方式。
- activities / tasks：邮件、电话、会议、跟进、提醒及操作时间线。
- opportunities：销售机会、阶段、预计金额和成交概率。
- products / price_lists / quotes / quote_items：产品、价格规则、报价版本和明细。
- orders / order_items / payments / shipments：订单、交付和付款跟踪。
- ai_tasks / ai_task_steps / tool_executions / approval_requests：AI 任务、步骤、工具执行、审批和审计。

当前初始 CRM 迁移仍是草稿，未应用到 Supabase。新增表或调整关系前，必须核对现有迁移，避免重复建模；所有新增数据表都要有经过审查的 RLS 与关系所有权检查。

## 获客任务流程

1. 用户定义目标国家、行业、客户类型、关键词、目标数量和渠道。
2. 连接器按平台授权、配额和速率限制获取候选企业。
3. 规范字段、校验来源、按企业主档去重。
4. 对官网、主营产品和公开业务信息做研究，记录证据。
5. 联系人和联系方式分开核验，未知字段保持未知。
6. 生成可解释的评分和推荐理由。
7. 将合格结果写入 leads，并记录来源、任务和审计。
8. 用户确认后转入客户管理；历史证据与活动不得丢失。

## 安全与自动化边界

- 默认允许研究、总结、评分和草稿生成。
- 对外发送邮件/WhatsApp、正式发送报价、确认订单等副作用操作，应执行权限检查和审批策略。
- 只能通过授权 API、许可数据供应商或允许访问的网页获取数据；不绕过登录、反机器人措施或平台访问控制。
- AI 输出是建议而非事实；每个关键判断应尽可能带来源和置信程度。
- 对外动作、数据修改和权限决策都必须记录审计事件。
